# An adaptable four-year plan

This is a schedule for a CS undergraduate building data/ML competence alongside a degree. S1–S8 mean your semesters, not fixed calendar years. College work can satisfy a module when you demonstrate its outcomes; avoid repeating a complete course merely to tick another box.

The example emphasizes ML/software engineering. For analyst, AI-application or research goals, substitute the corresponding [role pathway](practitioner-track.md#role-pathways). Free lectures and paid or free principal books follow the same [resource defaults](how-to-read-a-module.md#pick-one).

**First-year BTech CSE/AI student in India and undecided about your role?** Use the [India undergraduate path](india-undergraduate-path.md) to adapt this example. Begin with programming, your college mathematics and a small project; explore roles through actual work before committing to a specialization. An international-company goal does not require choosing a permanent job title in your first year.

<a id="the-bar"></a>
## What completion means

Build understanding and reviewable work. A job offer, internship, competition medal, public user count or coding-platform rating is not a semester pass condition. Those outcomes depend on circumstances beyond curriculum completion. Assess the work using the [learning contract](../curriculum/README.md#learning-contract).

<a id="four-tracks"></a>
<a id="weekly-template"></a>
## A sustainable week

For S1, use the [canonical semester workload](first-semester.md#semester-plan): roughly **5–7 hours outside college per week** as an adjustable planning assumption, including practice, projects and reflection. It is one budget, not extra hours for each guide.

In later terms, set the budget from your actual capacity and chosen project. Introduce interview practice once its prerequisites are comfortable and within that same budget. Reduce or pause work during exams, illness or caregiving; use the [recovery path](first-semester.md#recovery). The [six-week study pilot](study-pilot.md#six-week-review) shows how evidence changes the estimate.

## Module map

**CORE:** complete the stated core and artifact. **COLLEGE:** use degree teaching, fill specific gaps and demonstrate the artifact. **SELECT:** take if your role/project needs it. Advanced lists are never automatically mandatory.

| Module | Suggested term | Decision and retained outcome |
|---|---|---|
| M0 | S1–S2 | SELECT: flagged algebra/precalculus and proof practice; placement is optional and non-gating |
| M1 | S1 | CORE: beginner project, tested Weather CLI, environment and README |
| M2 | S2–Summer 1 | COLLEGE: derivatives/integrals, gradients, chain rule and optimization lab |
| M3 | S2–Summer 1 | COLLEGE: systems, subspaces, projections, eigenvalues/SVD and numerical checks |
| M4 | S2–S3 | CORE: data structures, algorithm design, correctness and complexity |
| M5 | Summer 1–early S3 | CORE: probability and simulation before inference/modeling |
| M6 | S3 | CORE: estimands, uncertainty, inference and decision limits |
| M6½ | S4 | CORE for DS: randomized design, power, identification and a decision memo |
| M7 | S2 | CORE: messy-data audit, validated transformations and plots |
| M8a | S2 | CORE: SQL, schema/migrations, query plans and anomaly memo |
| M8b | S6 | SELECT for MLE; CORE for data engineering: replay, data contracts and distributed trade-offs |
| M9 | S3, after M2/M3/M5 | CORE: regression from scratch and leakage-safe evaluation |
| M10 | S3, after M9 | CORE: classification, calibration, thresholds and slices |
| M11 | S3–S4 | CORE: K-Means/PCA; mixtures are deeper study |
| M12 | S3–S4, after M10 | CORE: tree implementation and model comparison |
| M13 | S6–S8 | SELECT: Bayesian modeling, sampling diagnostics and sensitivity |
| M14 | S6–S8 | SELECT: forecast baselines, rolling origins and honest intervals |
| M15 | S4 | CORE for MLE: numerical backprop checks and small PyTorch model |
| M16 | S4–S5 | SELECT for DL/LLM roles: tiny transformer and representation evaluation |
| M17 | S6–S8 | SELECT: RL only when the role/research question needs it |
| M18 | S5 | SELECT full post-training after M16; application route uses M18-app after M1 |
| M21 | S5 | SELECT for retrieval applications: frozen evaluation and baseline comparisons |
| M22 | S6 | SELECT for tool workflows: bounded dispatch, permissions, recovery and traces |
| M23 | S5–S6 | Relevant threat/evaluation core before releasing an AI system; advanced alignment optional |
| M24 | S6, incremental earlier | CORE: production bar applied to an existing evaluated project |

The [complete inventory](practitioner-track.md#prerequisites) controls dependencies. Term placement does not waive them. In particular, finish M5 before M6 and finish the relevant math before M9; M17 is optional, not a hidden M18 gate.

<a id="yearly-review"></a>
## Yearly direction review

Use these checkpoints at the end of each academic year, adjusting for your degree's course order and actual progress. Revisit earlier if a project or internship changes what you want to learn.

| Checkpoint | Evidence and next decision |
|---|---|
| Year 1: build a base and explore | Review your programming project and college mathematics. Choose one small next project that helps distinguish an interest in software, data analysis or AI applications; do not start all six routes. |
| Year 2: choose a provisional direction | Compare the work you enjoyed and could explain independently. Pick one primary route for the next term, retaining room for one adjacent exploration and unfinished CS fundamentals. |
| Year 3: test the direction against practice | Use project/internship feedback and a dated sample of relevant entry-level requirements. Keep, refine or change the route; fill demonstrated gaps before adding another framework. |
| Year 4: focus the transition | Review the capstone, degree progress and actual application requirements. Choose the next work or study step from current evidence and circumstances; a different outcome can justify revising the plan. |

Keep a short decision note: evidence reviewed, what changed, what stays useful and the next review date. The [career guide](career-operations.md#skills-checklist) explains how to sample current requirements; a sample supports a planning decision, not a forecast of the market at graduation.

<a id="semester-plan"></a>
## Semester checkpoints

<a id="s1"></a>
### S1: Python and study habits

Follow the [first-semester schedule](first-semester.md#semester-plan), which integrates Week 0, the first month and M1 projects. Use college maths to fill specific gaps. **Exit evidence:** [M1 readiness](readiness-checks.md#m1-ready), a tested CLI, reproducible setup and an honest memo. If ready and time remains, the final SQL/data investigation is a preview; full M7/M8a remains S2 work. Completing a calendar week does not certify a module.

<a id="s2"></a>
### S2: Data and mathematical tools

M7 + M8a share a data pipeline; begin M2/M3 and M4 with college courses. **Exit evidence:** documented schema, reproducible transformations, validation failures and understandable plots. Keep numerical-math work progressing before S3.

<a id="summer-1"></a>
### Summer 1: Consolidate prerequisites

Complete the M2/M3 core and begin/complete M5 at a sustainable pace. Package the existing data project; learn shell, Git and an API only as needed. **Exit evidence:** numerical checks, probability simulations and a fresh-environment reproduction. Employment or a merged external PR is not required.

<a id="s3"></a>
### S3: Inference and classical models

Finish M5, then M6; complete M9 → M10 → M12, with M11 alongside when ready. Reduce scope or carry M11/M12 to S4 if the term is overloaded. **Exit evidence:** train-only pipelines, untouched evaluation data, baseline comparison, calibration or residual analysis and subgroup errors.

<a id="s4"></a>
### S4: Deep learning or domain depth

MLE route: M15, then M16 if needed. DS route: M6½ plus a domain analysis. **Exit evidence:** one controlled experiment with clear hypotheses, measured uncertainty and a report; DL work includes gradient checks and an evaluated small model. Do not add mandatory RL or another unrelated flagship.

<a id="summer-2"></a>
### Summer 2: Collaboration

An internship, research project, open-source contribution or peer-reviewed local project can provide feedback. Use only material you have permission to share. **Exit evidence:** a reviewable contribution, response to feedback and a results memo. Prepare applications around actual program deadlines.

<a id="s5"></a>
### S5: Specialize

AI route: full M18 after M16, or M18-app for application work, then M21. Introduce M23 threat tests immediately. Other routes choose M13/M14 or deepen the existing model project. **Exit evidence:** one useful comparison with a frozen evaluation set and explicit limitations.

<a id="s6"></a>
### S6: Operate and recover

Complete M24 on that project. Data engineers add M8b; agent applications add M22 then the corresponding M23 tests. M25/brief supplies a product decision. **Exit evidence:** CI, versioned artifacts, metrics, a failure drill and rollback, locally if preferred.

<a id="summer-3"></a>
### Summer 3: Select the capstone question

Consolidate feedback and identify one unsolved question. Prepare a small proposal: audience, baseline, data rights, evaluation, resource budget and risk. Choose the [M26 track](../curriculum/6-frontier-production.md#module-26) before increasing scope.

<a id="s7"></a>
### S7: Capstone first result

Implement the simplest test of the question, obtain feedback and record a negative result if it occurs. Practice explaining the architecture or method. **Exit evidence:** reproducible baseline, first evaluation and a scoped revision plan.

<a id="s8"></a>
### S8: Complete and communicate

Run the final evaluation, write the report/runbook and prepare a sanitized or private demo. **Exit evidence:** the selected M26 rubric is satisfied and a reviewer can reproduce the central result. Apply for relevant work or further study alongside the project; an offer is not a curriculum pass condition.

<a id="flagship-projects"></a>
## A small number of evolving projects

| Project | Can cover | Essential evidence |
|---|---|---|
| P0 Weather CLI | M1 | Input/error tests, mocked service behavior, README and memo |
| P1 Data/analysis pipeline | M7, M8a, M6, M6½, M25 where applicable | Schema, transformations, uncertainty/identification, query plans and decision |
| P2 Predictive service | M9–M12, M15 when relevant, M24 | Honest split, baseline, training/evaluation, artifacts, operational checks |
| P3 AI application or research extension | M18/M18-app, M21–M24 or relevant research modules | Retrieval/model/agent evaluation appropriate to actual capabilities |
| Capstone | M26 | A deeper question built on the strongest existing project |

Tag milestones and map each requirement to evidence. Multiple repositories, arbitrary coverage percentages, minimum public users and cloud deployment are not required.

<a id="dsa-ladder"></a>
## Interview practice

Start with arrays, strings, maps and complexity; progress to recursion, trees/graphs, then dynamic programming when relevant. Re-solve missed problems and explain a solution's correctness and complexity. Timed practice follows understanding. Use the target role's actual interview format; SQL and experiment-design practice may matter more than contest programming for an analyst.

<a id="cs-core"></a>
## CS foundations

Use your degree's actual syllabus and labs as the starting point. Add the following evidence when the relevant coursework arrives; these are not five extra courses to finish in Year 1. A college assignment can satisfy a roadmap outcome when you can explain, reproduce and extend it, while any missing outcome remains explicit.

| College topic | Evidence to retain and demonstrate |
|---|---|
| Data structures and algorithms | Implement and test a structure or algorithm; explain correctness, time/space complexity and a trade-off. Map relevant work to M4. |
| Operating systems | Explain processes, memory and concurrency through a small lab, including an observed race, resource limit or scheduling behavior. |
| Computer networks | Trace a request through DNS, transport and HTTP; diagnose a timeout or connection failure using a small client/server example. |
| Databases | Design keys and constraints, write joins, explain a transaction and compare a query plan. Map matching schema/query work to M8a. |
| Software design | Improve a small application with clear interfaces, tests, version control and a documented design decision; reuse it in later module projects. |

Fill a specific gap with free resources such as [MIT Missing Semester](https://missing.csail.mit.edu/), [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/) or [CMU Database Systems](https://15445.courses.cs.cmu.edu/). DDIA is a recommended paid systems reference, not a free lecture course. Keep the examples and any remaining gaps in the [progress tracker](progress-tracker.md).

Check official terms before investing in an application: current cycle, student status, country/institution eligibility, funding, workload and deadlines. The following are leads, not verified promises about future availability or stipends.

|---|---|

| Research internships | [Summer@EPFL](https://summer.epfl.ch/), [ETH fellowship](https://inf.ethz.ch/studies/summer-research-fellowship.html), [Max Planck](https://www.cis.mpg.de/internships/) |

At the start of each term, check your shortlisted programs. Save each real deadline with its source/date, prerequisites and next action. Review the list monthly; plan references and proposals backwards from confirmed deadlines. An old calendar is not evidence for a future cycle.

<a id="checkpoints"></a>
## If the plan slips

Use completed artifacts to diagnose the obstacle. Reduce optional topics, reuse a project, revisit a prerequisite or extend the schedule. Seek feedback on a specific gap. Do not automatically respond with more applications or more problem quotas; evidence about your own situation should determine the next step.
